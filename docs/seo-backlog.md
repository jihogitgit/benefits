### 2. 새 66장의 색인 추적

2026-09-23에 사이트맵에 올렸다. 색인은 요청과 무관하게 수 주 걸린다. 볼 것:

- 비교 페이지가 실제로 색인되는가 (얇은 목록으로 판정되면 안 된다)
- 상세 페이지의 "색인이 생성되지 않음"이 줄어드는가 — 이게 66장을 연 진짜 목적이다

줄지 않으면 원인이 인바운드 링크가 아니었다는 뜻이고, 비교 페이지는 되돌릴 수 있다
(`compareEntries`를 사이트맵에서 빼면 된다. 페이지 자체는 noindex로 남는다).

**기준선 (2026-09-23, GSC 내보내기).** 나중에 "늘었다"고 말하려면 그 전 숫자가 있어야 한다.

| 항목 | 값 |
|---|---|
| 데이터 구간 | 2026-09-14 ~ 09-20 (7일). 필터는 3개월인데 그 전이 비었다 — 속성 인증이 9/14쯤 |
| 클릭 / 노출 | **0 / 19** |
| 노출된 페이지 | 8장 (지원금 상세 4 · 홈 2 · 가이드 2 · 비교 0) |
| 검색어 | **0행.** 노출이 구글의 임계값 아래라 아예 안 나온다 |
| 게재 순위 | 1~7위 |
| 사이트맵 | 164 URL |

검색어가 0행이라 1번(가이드 문구·새 주제)은 이 내보내기로 풀리지 않는다. **10월 하순에
다시 받는다.**

**색인을 막는 것은 없다 (2026-09-23 운영 실측).** `robots.txt` `Allow: /` · 사이트맵 5개
등재 · `/sitemap.xml` 200 · 비교 페이지 `index, follow` · canonical 자기 참조 ·
`http://`와 `www.` 둘 다 308. 6주 뒤에 "사실 막혀 있었다"가 나올 일은 없다.

**얇음은 실재했고 손봤다.** 66장 실측 결과 전체 654~917자 중 **425자가 66장 공통 푸터**였고
고유 텍스트는 229~355자, 그마저 대부분 지자체 이름 나열이었다. 「지자체마다 갈리는 대목」
절을 붙여 고유 텍스트 중앙값이 **692 → 817자**가 됐다(63/66장에 실림. 나머지 3장은 모든
축이 전부/전무라 비워 뒀다). 무엇을 실을지 정한 측정은 `npm run measure:compare`,
축을 고른 근거는 `src/lib/benefits/compare-facts.ts` 주석.

늘어난 폭이 크지 않다는 것은 분명히 해 둔다. 이걸로 색인이 붙는다는 보장은 없고, 6주 뒤에
안 붙으면 남은 설명은 둘이다 — 지자체 목록이라는 형식 자체가 얇거나, 인바운드 링크가

### 3. 금액 비교 (축 정의가 먼저)

비교는 1,365장에 붙는 사실 주장이다. 파싱이 틀리면 수천 장이 거짓말을 한다.

### 6. 제외 조건·중복수급 — 측정하고 접었다

외부 분석이 "제외 조건 블록(비용 거의 0)"과 "중복수급 판정(아무도 못 따라옴)"을 권했다.
만들기 전에 원문 분포를 셌고(`npm run measure:exclusion`), 그 결과로 **둘 다 접는다.**

status=open 10,482건 기준:

| | title | summary | amount_text | target_text | criteria_text |
|---|---:|---:|---:|---:|---:|
| 채움률 | 100% | 100% | 100% | 100% | **9.8%** |
| 중복 불가/제한 | 0 | 4 | 52 | 53 | 5 |
| 자격 제외 (좁게) | 0 | 5 | 184 | 219 | 20 |
| 제외 (넓게) | 4 | 37 | 783 | 846 | 110 |

세 가지가 걸린다.

- **`criteria_text`는 9.8%뿐이다.** 제외·중복 문구는 거기가 아니라 `target_text`와
  `amount_text`에 실려 있다. "자격 조건은 criteria_text에 있다"는 해설 발행분(28건)에서
  얻은 인상이고, 전 건에는 해당하지 않는다.
- **모수가 안 된다.** 중복 불가/제한은 어느 필드로 세도 100건 안팎, 전체의 1%다.
  관계도를 만들 양이 아니다.
- **걸린 문장 대부분이 사람 자격과 무관하다.** 좁힌 패턴의 상위 표본이
  `점심시간 12:00 ~ 13:00 제외`, `일반인에게 분양되는 복리시설은 제외`,
  `상해사고로 사망한 경우(15세 미만자 제외)`다. 기계로 뽑아 "당신은 못 받습니다"로
  보여주면 3번(금액 비교)이 경고한 것과 같은 사고가 난다 — 다만 이쪽이 더 나쁘다.
  금액 오표기는 확인하면 드러나지만, 자격 오표기는 사용자가 신청을 포기하게 만든다.

접는 대신 남는 길: 해설 발행분처럼 **사람이 검수한 행에만** 제외 조건을 손으로 적는다.
이건 가이드 작업이지 파싱 작업이 아니다.

첫 측정에서 `기수혜/기지원` 89건이 나왔는데 전부 오탐이었다(`/기\s*(수혜|지원)/`이
'보청기 지원'의 '기 지원'에 걸렸다). 패턴을 고쳐 5건이 됐다. 이 표의 숫자는 고친 뒤 값이다.

### 7. 조건 코드가 실제로 덮는 범위 (계산기·생애이벤트를 정하기 전 측정)

`benefit_conditions` 행은 10,482건 전부에 있지만, 축별로 값이 든 비율은 다르다.

| 축 | 값이 있는 지원금 | 비율 |
|---|---:|---:|
| `income_bands` | 1,817 | 17.3% |
| `life_stages` | 1,974 | 18.8% |
| `household_types` | 2,347 | 22.4% |
| `occupations` | 2,388 | 22.8% |

소득 구간은 `0-50`에 쏠려 있다(1,758 / 519 / 232 / 52 / 46). 중위소득 계산기를
"통과하는 지원금 N개"로 연결하면, 50% 이하인 사람에게는 1,758건이 걸리지만
101% 이상인 사람에게는 98건뿐이고 나머지는 소득 조건이 아예 없는 8,665건이 채운다.
`matchScore`(search.ts)가 조건 없는 행을 0점으로 뒤로 보내므로 결과는 성기게 나온다.

생애이벤트는 원천 코드가 **출산·임신·학령기까지만** 있다.

```
life_stages:      birth 766 · high_school 736 · middle_school 612 ·
                  elementary 550 · pregnancy 319 · pre_parent 154
household_types:  disabled 894 · veteran 743 · multi_child 221 · no_house 172 ·
                  multicultural 163 · single_parent 156 · new_resident 126 …
occupations:      farmer 1052 · livestock 598 · college 387 · job_seeker 314 …
```

외부 분석이 제안한 열 개(`출산 이사 퇴사 폐업 장례 암진단 육아휴직` …) 중 조건 코드로
뒷받침되는 것은 **출산·임신·학령기·구직** 넷이고, 이사는 `new_resident` 126건으로 얇다.
퇴사·폐업·장례·암진단은 대응 코드가 없어 키워드 검색에 기대야 하는데, 그러면 정확도가
조건 매칭이 아니라 제목 문자열 수준으로 떨어진다. **넷으로 시작하고 나머지는 열지 않는다.**

`occupations`의 `small_biz`가 10건뿐인 것은 별개 문제다. 소상공인 분류는 조건 코드가
아니라 `src/lib/segments/rules.ts`가 제목·대상 문구로 판정한다. 두 기준이 다르다는 사실만
적어 둔다.

### 8. 연간 신청 캘린더 — 데이터가 없어 접는다

외부 분석이 `/calendar`를 권했다. "청년월세 3~5월 / 근로장려금 5월·9월 반기 /
국가장학금 학기별" 처럼 월별로 늘어놓자는 것이다. 만들기 전에 날짜 데이터를 셌다.

```
전체 10,968건 중  apply_start 있음 481 (4.4%) · apply_end 있음 616 (5.6%)
접수 시작 연도별   2023: 28 · 2024: 26 · 2025: 99 · 2026: 322
접수 시작 월별     1월 153 · 3월 92 · 2월 65 · 나머지 달은 6~25
```

두 가지가 걸린다.

- **모수가 4.4%다.** 나머지 95%는 `deadline_type`이 상시이거나 날짜가 비어 있다.
  월별로 흩어 놓으면 한 달에 스무 건 남짓이고, 그마저 1월에 몰려 있다(연 단위 사업이
  1월에 시작해서다). 달력 모양은 만들 수 있지만 달력이 말하는 내용이 없다.
- **과거 이력이 없다.** 동기화는 현재 상태만 들고 closed로 바뀐 445건이 전부다.
  "작년 이맘때 열렸다"를 말할 근거가 2024년 26건뿐이다.

분석이 예로 든 프로그램들(청년월세·근로장려금·국가장학금·에너지바우처)은 전부 이 표에
날짜가 없는 대형 국가사업이다. 즉 제안된 캘린더는 **데이터에서 나오지 않고 사람이 적는
글**이다. 그건 가이드 작업이고, 가이드 순서는 1번(GSC 검색어)이 풀려야 정한다.

데이터 기반 `/calendar`는 접는다. 사람이 쓰는 형태는 가이드 백로그로 넘긴다.

### 9. 마감 알림 (이메일) — 보류

전달 수단을 이메일로 정했고, 필요한 판단까지는 내렸다. 구현은 하지 않는다 — 보낼 수단이
없는 상태에서 구독 폼만 띄우면 사용자에게 거짓말이 된다.

**착수하려면 셋이 필요하다.**

1. **발송 서비스.** Vercel 마켓플레이스 `messaging`에는 **Resend 하나뿐**이다
   (`vercel integration discover --category messaging`으로 확인. `productivity`·`dev-tools`도
   훑었고 이메일 발송은 없다). 마켓플레이스 밖(SendGrid·Mailgun·SES 등)을 쓰면 SDK 배선과
   키 관리, 실패 처리를 이 저장소가 직접 들고 간다. `vercel integration add resend/resend-email`은
   사용자 팀에 실제 리소스를 만들고 과금 대상이 되므로 사람이 승인해야 한다.
2. **도메인 인증.** `naemok.com`에 SPF·DKIM·DMARC. 어느 서비스를 쓰든 이게 없으면
   스팸함으로 간다. 구글 소유확인을 DNS TXT로 해 둔 것과 같은 자리다(1절).
3. **마이그레이션 실행.** 아래 표를 만드는 SQL. 초안을 썼다가 지웠다 — 실행하지 않을
   마이그레이션을 번호에 남기면 저장소는 006인데 DB는 005인 상태가 되고, 다음 사람이
   없는 기능의 표를 만들게 된다. 착수할 때 다시 쓴다.

**초안에서 내린 판단(다시 쓸 때 같은 자리를 밟지 않게).**

- **이중 확인(double opt-in).** 입력칸에 남의 주소를 적을 수 있다. 확인 없이 보내면 우리가
  원치 않는 메일을 보내는 쪽이 되고, 도메인 평판이 망가지면 이후 모든 메일이 스팸함으로 간다.
  `confirmed_at`이 null인 행에는 보내지 않는다.
- **토큰을 둘로 나눈다.** 확인용과 해지용이 같으면, 확인 메일이 전달된 제3자가 그 링크로
  해지까지 할 수 있고 반대도 성립한다.
- **RLS를 켜고 정책을 하나도 만들지 않는다.** 브라우저가 이 표에 닿으면 이메일로 남의 구독
  목록을 조회할 수 있다. 구독·확인·해지는 전부 service role 서버 라우트가 하고 거기서
  레이트 리밋을 건다.
- **`benefit_slug`에 외래키를 걸지 않는다.** 슬러그 체계가 바뀌었을 때 구독이 통째로
  사라지는 쪽이 알림이 조용히 멈추는 것보다 나쁘다. 발송 시점에 조인해 없으면 건너뛴다.
- **`days_before`를 열로 둔다.** 지금은 3일 하나지만 7일·1일을 더할 때 표를 안 바꿔도 된다.
- **한 구독당 한 번만 보낸다**(`notified_at`), **실패 사유를 남긴다**(`last_error`).

**적어 두는 대안.** 한국 사용자 대상이라면 카카오 알림톡의 도달·열람률이 이메일보다 확연히
높다. 비즈니스 채널·발신 프로필·템플릿 심사가 필요해 착수 비용이 크다. "이메일이 잘 안
열린다"는 결론에 도달했을 때의 다음 수다.
